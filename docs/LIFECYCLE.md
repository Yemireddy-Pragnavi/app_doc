# Security lifecycle implementation

This extends the existing application. It does not replace authentication, the database, scans, launch reviews, findings, or the Violet Dusk design.

## Available in this increment

- Historical security graph snapshots are stored with new repository scans in PostgreSQL JSON. Older scans receive a clearly labeled metadata-only graph. Nodes and relationships have stable identifiers, source evidence, and inference labels. Extraction covers existing components, literal routes, local imports, Python functions/local calls, dependencies, SQL table declarations, environment-variable names, security-related files, workflow declarations, deployment configuration, and redacted findings.
- React Flow views include component filtering, node details, zoom/pan, upstream/downstream tracing, potential paths, changed components, and full-screen mode. Data-flow and runtime views explicitly distinguish static associations from observed behavior. They do not assert that data actually moved or that a component without findings is healthy.
- Architecture comparisons identify added/removed nodes and edges and changed control/manifest revisions. Same-branch complete assessments support score-regression detection. Cross-branch comparisons are available but do not imply chronological regression or causal proof.
- Risk prioritization preserves severity and explains route, runtime-response, and recurrence modifiers. Unknown reachability never suppresses findings. Authentication requirements, sensitive-data access, active-secret status, and exploitability remain unknown unless evidence supports them.
- Branch-specific security memory distinguishes repeated observations from a vulnerability disappearing and later reappearing. Partial scan absence never marks resolution. Timeline scores and recurrence counts derive from stored assessments.
- Versioned repository policies produce deterministic decisions. Evidence gaps fail closed. Policies include score thresholds, critical/high findings, secret candidates, regressions, external-service changes and required runtime evidence. Overrides require Owner/Admin authority, a reason, blocking finding references, an exact assessment and policy/evidence digest, and expire after 24 hours. New policy or runtime evidence invalidates an earlier override.
- Repository roles: Owner, Admin, Security Lead, Developer, Viewer. Owners explicitly grant access to existing signed-in users. Roles control lifecycle reads, policies, scans, acceptance records, remediation and overrides. Existing Phase 1 personal-workspace endpoints remain owner-scoped. Shared repositories are accessed in Security Lifecycle.
- Accepted/ignored risks are recorded with reasons and remain visible in evidence and policy decisions. They do not silently erase blockers.
- Narrow remediation: exact Python requirements.txt dependency pins can be upgraded to a reviewer-selected fixed version listed by the advisory. Generate a patch, review it, then explicitly create a **draft** PR using the reviewing developer's GitHub authorization. The base commit and reviewed content digest must still match. No arbitrary source code is executed and no uncertain business logic is rewritten. Compatibility and tests remain developer responsibilities. A failed external write retains its branch and reconciliation status.
- After a recorded PR is merged, verification requires a complete scan of its exact merge commit. Absence means “not detected in merge scan,” not a guarantee. Configure signed webhooks for automatic scans after pushes and merged PRs on explicit branches.
- The CI integration checks the exact commit using a hashed, repository-scoped, rotatable 30-day credential. Missing evidence, missing secrets or an unavailable backend fails the job. Require the GitHub Actions job in branch protection to enforce it.
- Portfolio summaries and shared-component associations include only repositories the viewer can access. A shared component name does not prove a shared deployed service or shared credential. No raw credential cross-repository matching is performed.
- Audit exports include bounded scan history, findings, graph snapshots, policy revisions and activity, including release decisions and overrides. They support review; they do not certify compliance.

## Operating the integrations

1. Deploy the existing Compose stack on a Docker-capable HTTPS host and configure GitHub OAuth, session signing, token encryption, and the frontend API URL as in SETUP.md. Run a repository scan to collect source-backed graph evidence.
2. Open Security Lifecycle, select the repository, and set its release policy. The default requires matching runtime evidence. Cloud declarations and runtime results retain their existing Phase 2 boundaries.
3. In Policies, configure/rotate a webhook. Copy the returned secret immediately. Configure GitHub repository webhook URL `https://YOUR_BACKEND/api/lifecycle/webhooks/github/REPOSITORY_ID`, JSON content, the returned secret, and push/pull_request events. Delivery signatures, repository identity, branch allowlist, duplicates and scan quotas are checked. Dispatch failures are recorded; start a manual scan after resolving a queue/quota problem.
4. Copy `integrations/github-actions/gate.py` into the consuming repository and the YAML example into `.github/workflows/security-gate.yml`. Set `ASD_URL` and `ASD_REPOSITORY_ID` repository variables and `ASD_GATE_TOKEN` as a secret. Make the App Security Doctor job a required check. Fork PRs have no secret and fail closed; never change the workflow to `pull_request_target` to expose it.
5. Do not delete legacy tables. Startup creates new lifecycle tables additively through SQLAlchemy metadata; no existing columns or data are rewritten. Back up PostgreSQL before production upgrades and run the test suite against a staging copy. Graph snapshots for historical scans cannot recover source that was never retained; rescan those commits/branches through your repository workflow.

## Still not complete against the entire attached specification

This is an implemented, bounded increment, **not a claim that all Phase 3/4 enterprise requirements are complete**. Remaining work includes organization tenancy and SSO/MFA enforcement, a GitHub App installation model, continuous analysis of open/fork PR heads and releases, verified cross-service identity/data-flow correlation, whole-program multi-language taint analysis, authenticated runtime crawling, live cloud management-plane checks, KEV enrichment, deployed secret validation, external Slack/email notifications, broader fix generators, automated compatibility testing in a separate build sandbox, billing/entitlements, robust webhook retry/outbox delivery, organization-wide controls, and production-scale retention/performance validation. UI node “expansion” is bounded graph tracing, not remote discovery. Runtime/source identity is reviewer declared, not independently attested.

The hosted Sites preview has no configured Python backend/OAuth. Lifecycle pages therefore show a connection requirement instead of fabricated activity. New backend workflows require live integration acceptance before production use.
